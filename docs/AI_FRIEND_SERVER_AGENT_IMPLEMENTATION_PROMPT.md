## 0. 먼저 읽을 실행 지시

너는 기존 OnTechChat 프로젝트를 확장하는 개발자다. 아래 요구를 실제 코드, 검증 가능한 실행 경로, 공식 빌드 산출물까지 구현하라. 계획이나 UI 목업만 만들고 완료로 보고하지 않는다.

사용자 요구:

> 친구 목록에 AI 친구가 있고, 그 친구와 질문·답변을 주고받는다. 이후 같은 채팅에서 프로그램 개발과 제어를 요청한다. 사용자는 별도의 OS를 갖지 않는다. 모든 작업은 OnTechChat이 설치된 서버 PC 한 대의 Windows에서 실행한다. 사용자마다 작업공간과 실행 권한을 분리하고, 일반 사용자가 다른 사용자나 관리자 영역에 접근하거나 권한을 올릴 수 없게 한다.

이 문서는 위 요구를 구체화한 권장 구현 계약이다. 사용자별 VM, Hyper-V 게스트, Windows Sandbox 게스트, 사용자 PC에 설치하는 별도 에이전트는 이번 아키텍처에 도입하지 않는다. Windows AppContainer는 같은 OS의 프로세스 권한 격리 기능이므로 사용 가능하다. 사용자에게 별도 Windows 로그인이나 바탕화면을 요구하지 않는다.

기존 AI 대화·모델·추론·대화 저장 기능을 보존하고 확장한다. 대화 UI, 앱 권한 검사, Windows 실행 권한, 공용 프로그램 제어를 각각 구현해야 한다. LLM 출력이나 시스템 프롬프트를 권한 판단 근거로 사용하지 않는다.

진행 순서: 프로젝트 지침 확인 → 현재 상태 기록 → AI 친구 → 권한·데이터 이행 → 실행기 격리 실증 → 에이전트 도구 루프 → 등록 프로그램 제어 → 통합 UI·검증·빌드.

## 1. 작업 경계와 완료 범위

### 1.1 기본 구현 범위

1. 친구 목록의 기본 AI 친구 `온테크 AI`, 사용자별 기존 대화 이어가기·새 대화.
2. `user / admin / superadmin` 역할과 작업공간·프로그램별 명시적 권한.
3. 서버 PC 내부의 영속적인 사용자별 프로젝트 저장공간.
4. 같은 Windows에서 사용자별 AppContainer 보안 식별자로 실행되는 제한된 작업 프로세스.
5. 채팅의 명시적인 작업 모드에서 실제 LLM 도구 요청 → 파일 작성 → 빌드·실행 → 결과 전달.

8. 자동 검증, 실제 Windows 격리 검증, 공식 빌드, 사용자 문서.

### 1.2 후속 확장으로 남기는 범위

- 모든 Windows 프로그램을 임의로 클릭하는 범용 화면 자동화.
- 사용자별 원격 바탕화면, 전체 화면 스트리밍, 사용자별 OS.
- GPU 학습, 무제한 장기 실행 서비스, 드라이버 설치, 장비 제어 전체 자동화.
- 기존 AI 채팅의 토큰 스트리밍 개선은 필수 완료 조건이 아니다. 작업 상태·로그·최종 결과 갱신은 필수다.

GUI 전용 프로그램은 세션 보조 프로그램으로 확장 가능한 인터페이스를 두되, 실제 검증 없이 지원 완료로 표시하지 않는다. 프로그램 자체의 API·CLI 제어가 가능한 예제로 기본 제어 기능을 끝까지 검증한다.

### 1.3 개발과 운영의 구분

- 이번 실행 지시는 소스 수정, 격리된 개발 테스트, 공식 빌드·설치기 준비를 대상으로 한다.
- 운영 서비스 교체·재시작, 실제 사용자 데이터 이행, 운영 계정·방화벽·ACL 변경, 실제 업무 프로그램 시작·종료는 별도 운영 적용 지시가 있을 때 수행한다.

## 4. 사용자 경험: AI 친구와 작업 모드

### 4.1 AI 친구

- 친구 목록 상단에 별도 `AI 친구` 영역을 두고 `온테크 AI`를 표시한다.
- 로그인 가능한 가짜 User 계정, 공용 사용자 비밀번호, 모든 사용자가 공유하는 AI 방을 만들지 않는다.
- AIProfile은 서버가 관리하는 별도 리소스다. 초기 프로필은 1개로 충분하며 모델마다 친구를 복제하지 않는다.
- 프로필 선택 시 본인에게 연결된 기본 AI 대화를 연다. 없으면 한 트랜잭션에서 생성·연결한다.
- 더블 클릭, 모바일 연속 탭, 재전송 시 기본 방이 여러 개 생기지 않게 한다.
- 동일한 AI 친구가 보여도 사용자별 대화·프로젝트·도구 기록·임시 파일은 독립이다.
- AI 친구 프로필에 위치 조회·사람 친구 초대·비밀번호 변경 기능을 노출하지 않는다.
- 채팅 목록의 AI 표시, 모델·추론 선택, 고정, 과거 대화, 취소·재시도를 유지한다.
- AI 비활성·모델 없음은 친구 카드에서 이유를 표시한다. 사용 가능한 것처럼 가짜 대화를 만들지 않는다.

### 4.2 기존 AI 방 이행

- 기존 AI 방은 소유권·ID·모델·추론·메시지를 보존하고 기본 AIProfile에 연결한다.
- 기존 방이 여러 개면 사용자별 가장 최근 사용한 정상 AI 방을 기본 연결로 고른다. 동률은 안정적인 ID 정렬로 결정한다.
- 선택되지 않은 방도 채팅 목록에 그대로 남긴다. 이력 병합·문맥 공유를 하지 않는다.
- `새 대화`는 기존 방과 별개의 문맥을 만든다. 새 대화를 만든 사용자는 그 방을 기본 이어가기 대상으로 선택할 수 있다.
- 생성·이행·기본 연결 갱신은 동시 요청과 재시작 후에도 일관돼야 한다.

### 4.3 대화 모드와 작업 모드

- 기본은 `대화`다. 설명이나 코드 답변을 했다는 이유로 파일 생성·실행을 자동 수행하지 않는다.
- `작업` 모드에서는 대상 프로젝트와 허용 작업을 표시하고 사용자의 명시적인 작업 요청을 처리한다.
- 허용된 프로젝트 작업은 설정된 정책과 요청 범위 안에서 자동 진행한다. 모든 파일 읽기마다 승인 창을 띄우지 않는다.
- 등록 프로그램 제어는 대상 프로그램·동작을 표시한다. 추가 승인이 필요한 동작은 정책에 따라 승인 후 실행한다.
- 권한이 없는 동작은 승인 창으로 우회하지 않고 거절한다. 승인자는 해당 작업을 승인할 실제 권한이 있어야 한다.
- AI 답변, 실행 로그, 결과 파일, 실제 실행 여부를 구분한다. `코드를 작성했습니다`와 `빌드·실행에 성공했습니다`를 같은 상태로 표시하지 않는다.

## 5. 권한 모델과 역할 이행

### 5.1 역할별 기본 정책

| 기능 | user | admin | superadmin |
|---|---|---|---|
| 개인 AI 대화 | 허용 | 허용 | 허용 |
| 본인 프로젝트 개발·실행 | agent 사용 허가와 한도 내 | 동일 | 동일 |
| 타인 개인 대화 조회 | 금지 | 자동 허용하지 않음 | 자동 허용하지 않음 |
| 타인 작업공간 | 금지 | 명시적으로 위임된 범위만 | 별도 명시적 권한으로 접근·감사 |
| 일반 사용자 생성·중지·한도 관리 | 금지 | 관리 대상으로 위임된 사용자만 | 허용 |
| 동급·상위 계정 변경 | 금지 | 금지 | 별도 최고관리자 관리 정책 적용 |
| 역할 부여·승격·강등 | 금지 | 금지 | 재인증·감사·마지막 최고관리자 보호 |
| AI credential·실행기·보안 정책 설정 | 금지 | 기본 금지 | 허용 |
| 등록 프로그램 사용 | 명시적 grant의 허용 동작만 | 동일, 관리 범위 추가 가능 | 동일, 등록·정책 관리 가능 |

권한은 `역할 + 대상 소유권/위임 + 허용 동작 + 현재 상태`의 교집합이다. 숫자 등급 비교 하나나 프런트 버튼 숨김으로 구현하지 않는다.

최고관리자 역할도 생성 코드를 Windows 관리자 권한으로 실행할 권한을 자동 부여하지 않는다. OS 관리자와 앱 관리자는 서로 다른 개념이다. 앱 권한은 서버 PC의 실제 OS 관리자로부터 절대적으로 데이터를 숨기는 보안 경계가 아니다.

### 5.2 기존 사용자 이행

- 기존 admin은 종전 시스템의 최고 권한 계정이었다. 버전 있는 1회 마이그레이션으로 기존 admin을 superadmin에 대응시켜 기존 관리 권한을 보존한다.
- 일반 user는 그대로 유지한다. 이후 새 계정은 기본 user이며 자동 승격하지 않는다.
- 이행 전 백업, 변환 대상 수, schema 버전, 성공 여부를 기록한다. 비밀번호·대화 원문은 감사 로그에 남기지 않는다.
- 이행은 원자적·멱등적으로 처리한다. 실패하면 부분 저장하지 않으며 재실행해도 재승격을 반복하지 않는다.
- 최고관리자가 0명이 되는 중지·삭제·강등은 동시 요청에서도 막는다. 기존 관리자 부재의 비정상 데이터에 임의 계정을 승격하지 않는다.
- 역할 변경 전후의 공개 API 응답·UI를 같이 수정한다. `role === 'admin'`과 `Role == "admin"` 등을 검색하여 필요한 권한 함수로 교체한다.
- 기존 메일·FCM·사용자 관리·설정 적용 권한이 실수로 없어지거나 새 admin에게 과도하게 열리지 않도록 회귀 검증한다.

### 5.3 모든 경계에서 재검사

- 요청 수락, 큐 실행 직전, 각 도구 호출 직전, 결과 조회·다운로드 시 현재 권한을 검사한다.
- user_id, owner_id, role, root 경로, 실행 토큰은 클라이언트·LLM이 정하지 않는다. 인증 세션과 서버 저장 상태에서 결정한다.
- 권한 회수·사용자 비활성화·프로젝트 접근 회수 시 대기 작업과 활성 작업을 중단한다. 이미 수행된 외부 동작을 취소로 되돌렸다고 주장하지 않는다.
- 관리자가 일반 사용자 비밀번호를 초기화할 수 있다면 사칭 위험이 있음을 고려한다. 설정 초기화·세션 폐기와 감사 기록을 남기며 `관리자도 절대 접근 불가능` 같은 표현을 쓰지 않는다.

## 6. 권장 서버 구조와 책임 분리

다음 논리적 경계를 만든다. 모든 구성은 동일 서버 PC에서 동작하며, 별도 배포 제품을 늘리지 않는다.

1. **채팅·인증 서버**: 세션, 대화, 공개 catalog, 소유권, 작업 상태·결과 전달.
2. **Agent Coordinator**: LLM 호출, 도구 요청 해석, 단계·시간·비용 한도, 작업 상태 조정.
3. **Policy/Broker**: 현재 사용자 권한 검사, 승인된 대상·작업만 실제 실행기로 전달.
4. **Sandbox Runner**: AppContainer에서 파일 처리·빌드·생성 프로그램 실행. 서버 비밀이나 공용 제어 권한 없음.
5. **Host Program Controller**: 등록 프로그램의 제한된 동작만 수행. 임의 명령 실행 인터페이스 없음.

Coordinator와 LLM credential은 생성 코드 실행 프로세스 밖에 둔다. CLI 로그인 파일, API 키, 서버 DB, 관리 세션을 작업공간에 복사하지 않는다.

Runner는 서버의 특별 실행 모드 또는 내부 helper로 패키징할 수 있다. 프로젝트의 통합 설치 EXE 정책을 유지한다. 공개 배포 파일을 서버·트레이·실행기로 임의 분할하지 않는다.

통신은 인증·권한 제한된 로컬 IPC로 한다. named pipe를 쓴다면 접근 ACL과 상대 프로세스/토큰을 검증한다. 파이프 이름이 어렵다는 것만으로 인증을 대신하지 않는다. 작업 ID와 사용자·프로젝트·허용 동작에 묶인 짧은 수명의 권한을 사용한다.

사용자 Runner가 Broker를 통해 더 넓은 파일 경로, 관리자 작업, 다른 사용자 작업을 실행시키는 권한 대행 취약점이 없어야 한다. IPC 입력도 외부 API와 동일하게 불신한다.

## 7. 데이터 계약과 저장

기존 저장소를 우선 확장하고 nil map·optional field·구버전 snapshot을 처리한다. 이름은 관례에 맞춰 변경할 수 있으나 다음 책임은 분리한다.

| 데이터 | 필요한 필드·관계 |
|---|---|
| AIProfile | id, name, avatar, enabled, 기본 model_id, 설명 |
| 사용자 AI 기본 연결 | user_id + ai_profile_id → room_id |
| Project/Workspace | id, owner_id, 표시명, 서버 생성 storage_key, 상태, quota, timestamps |
| AccessGrant | subject, resource_type, resource_id, actions, 만료·회수 상태, 발급자 |
| AgentJob | id, owner_id, room_id, project_id, client_id, mode, 상태, 요청 model/effort, policy revision, 시각 |
| AgentStep/ToolCall | job_id, step_id, tool_call_id, tool, 검증된 입력 요약, 상태, 소요 시간, result 참조 |
| Artifact | id, owner_id, project_id, job_id, 안전한 상대경로, 크기, hash, MIME, 보관 상태 |
| ProgramDefinition | id, 고정 실행 파일, 허용 actions, 인자 schema, 실행 계정 정책, 자원 잠금, revision |
| AuditEvent | actor, action, resource, job_id, 결과·거절 코드, 시각, 정책 revision |

- 역할, 경로, credential, 정책 revision은 LLM 출력으로 덮어쓸 수 없다.
- 작업 로그·파일 내용 전체를 기존 단일 스냅샷에 무제한 넣지 않는다. 메타데이터와 용량 제한된 로그·산출물을 구분한다.
- 대화 소유권과 프로젝트 위임 권한을 구분한다. 프로젝트 공동 관리 grant가 개인 대화 조회까지 열지 않는다.
- 감사 로그는 Runner가 쓰거나 수정할 수 없는 위치에 둔다. 관리자 접근도 기록한다.
- API 키·인증 토큰·비밀번호·원문 CLI 로그인 정보는 모델 문맥·로그·산출물에 넣지 않는다.
- 신규 `ai` 설정과 `agent` 설정을 구분한다. 구버전 설정 요청에 신규 필드가 없으면 기존 신규 설정을 유지한다.
- agent는 초기 기본 비활성으로 이행한다. 관리자가 실행기 진단과 권한 설정을 완료한 뒤 활성화한다.

## 8. Windows 실행 격리: 반드시 실제로 검증할 것

### 8.1 AppContainer 기본 계약

- 전용 비관리자 서비스 실행 컨텍스트 아래 사용자별로 안정적이고 서로 다른 AppContainer 프로필/SID를 사용한다. 하나의 프로필을 전 사용자에게 공유하지 않는다.
- 별도 Windows 사용자 로그인은 요구하지 않는다. 운영 실행 계정 설정은 공식 설치·서비스 수명주기에 통합한다.
- 실행 전 실제 토큰의 AppContainer 여부·SID·권한을 검사한다. 기대한 토큰과 다르면 실행 거절.
- 본인 프로젝트·전용 temp·cache에는 필요한 쓰기 권한, 승인된 도구 설치 경로에는 필요한 읽기·실행만 부여한다.
- 서버 운영 데이터·설정·홈·다른 사용자 workspace에는 권한을 부여하지 않는다. 광범위한 ALL APPLICATION PACKAGES 권한 부여로 해결하지 않는다.
- 환경변수는 명시적으로 구성한다. 사용자별 HOME/TEMP/cache를 분리하고 서버 credential·프로필을 그대로 상속하지 않는다. 이는 구현 앱의 자식 프로세스 환경 구성에 관한 요구다.
- 생성 코드뿐 아니라 빌드 도구·스크립트·테스트도 격리 안에서 실행한다. 빌드 파일과 패키지 설치 스크립트 역시 코드를 실행할 수 있다.
- 부모와 자식의 실행 토큰·접근 범위가 동일한 제한을 유지하는지 검증한다.
- 임의 프로그램·컴파일러가 AppContainer에서 모두 동작한다고 가정하지 않는다. Go를 첫 필수 실증 대상으로 삼고 Python/.NET 등은 확인된 항목만 enabled로 등록한다.
- LPAC 등 더 엄격한 모드는 호환성·필요 capability를 확인한 뒤 적용한다. 이름만 붙이고 격리 구현을 생략하지 않는다.

### 8.2 경로와 파일

- 외부에는 프로젝트 ID와 상대경로만 받는다. 실제 루트 경로는 서버가 저장된 storage_key로 결정한다.
- `..`, 절대경로, 다른 드라이브, 드라이브 상대경로, UNC, 장치 경로, ADS, 예약 이름 등 Windows 경로 우회를 거절한다.
- junction·symlink·reparse point·hard link를 이용한 외부 대상 접근과 검증 후 경로 교체 경합을 다룬다. 단순 문자열 prefix 검사로 끝내지 않는다.
- 파일의 최종 대상과 핸들 기준의 접근 범위를 확인하고, OS ACL/AppContainer를 최종 방어 경계로 유지한다.
- 파일 덮어쓰기·프로젝트 삭제는 리비전·활성 작업을 확인한다. active workspace를 동시에 정리하지 않는다.
- 결과 파일 조회·다운로드도 동일한 소유권 검사와 실제 경로 검증을 통과해야 한다.
- zip 등 아카이브 지원 시 경로 탈출·링크·총 해제 용량을 제한한다. 첫 버전에 필요하지 않으면 지원하지 않는다.

### 8.3 프로세스·자원·네트워크

- 작업별 Job Object에 프로세스를 연결한다. 시작 직후 실행이 빠져나가는 경합을 방지하도록 suspended 생성·할당·resume 등 검증된 순서를 사용한다.
- 자식이 Job을 탈출하는 설정은 허용하지 않는다. 취소·timeout·서버 종료 시 해당 Job의 프로세스만 종료한다.
- CPU·메모리·프로세스 수·실행 시간 한도를 둔다. Job Object는 파일 접근 샌드박스가 아니다.
- 디스크 한도는 별도로 구현한다. 파일 쓰기 API에서의 크기 검사만으로 임의 생성 코드의 디스크 쓰기까지 제한했다고 주장하지 않는다. 적용 가능한 실제 제한과 잔여 한계를 명시한다.
- 동시 작업 수와 큐 상한을 전역·사용자·프로젝트별로 설정한다. 특정 사용자가 큐를 독점하지 못하게 한다.
- 작업 프로세스의 네트워크는 기본 차단한다. 허용된 의존성 준비는 별도 중계·검증 경로를 사용한다.
- AppContainer internetClient capability만으로 특정 도메인 허용목록이 구현됐다고 보지 않는다. loopback·내부망·서버 관리 API·네트워크 IPC 우회도 검증한다.
- 출력 크기·로그 보관량·파일 보관량에 상한을 둔다. 채팅 서버 저장소 잠금을 잡은 채 외부 프로세스를 기다리지 않는다.

## 9. LLM과 도구 실행 연결: 실제 에이전트 구현

텍스트 답변을 저장하는 현재 AIExecutor만으로는 파일 작성·실행 에이전트가 완성되지 않는다. 다음 구조를 추가한다.

1. 사용자의 작업 모드 요청과 프로젝트를 서버가 검증한다.
2. 모델에는 그 작업에서 허용된 도구 schema와 제한된 프로젝트 문맥만 전달한다.
3. 모델이 구조화된 도구 요청을 반환한다.
4. 서버가 schema·권한·경로·한도·현재 상태를 검증한다.
5. 승인된 요청만 Broker/Runner로 실행한다.
6. 제한된 도구 결과를 모델에 반환해 다음 단계 또는 최종 답변을 받는다.
7. 실제 작업·산출물 상태를 저장하고 채팅에 결과를 표시한다.

도구 예시:

| 도구 | 서버가 강제할 범위 |
|---|---|
| `workspace.list/read` | 현재 project 내부, 크기·개수 제한 |
| `workspace.write/patch` | 현재 project 내부, 리비전·쓰기 한도 검사 |
| `build.run` | 등록된 toolchain, 검증된 입력, 격리 실행 |
| `program.run` | 현재 project의 지정 산출물, 격리 실행 |
| `job.status/cancel` | 본인 작업 또는 명시적 위임 |
| `host_program.action` | program_id + action + schema를 통과한 매개변수 |

- OpenAI 호환 연결은 해당 모델의 실제 tool_calls 지원을 확인하고 도구 왕복을 구현한다. 호환 HTTP라는 이유로 지원을 가정하지 않는다.
- Claude CLI를 planner로 쓸 경우 대화 전용 도구 차단은 유지한다. 지원되는 구조화 출력 방식으로 도구 제안을 받고 중앙 실행기가 처리한다. 지원 여부는 실제 설치 버전에서 확인한다.
- 구조화 출력이 없는 연결은 대화 전용으로 남길 수 있다. 에이전트 가능 연결이 하나도 없으면 agent 사용 가능으로 표시하지 않는다.
- 일반 답변의 코드 블록, Markdown, 임의 `{"command":...}` 문자열을 찾아 자동 실행하지 않는다. 지정된 구조화 응답의 엄격한 schema 검증이 필요하다.
- 모델이 owner_id, 실행 파일 절대경로, 권한, API 키, 임의 서버 도구를 추가하면 거절한다.
- 파일·로그·프로그램 출력에 적힌 지시문은 데이터다. `관리자로 실행`, `이 토큰으로 다른 프로젝트 접근` 같은 내용으로 권한이 바뀌지 않는다.
- 모델·추론은 기존 resolver를 재사용하고 요청 시점의 선택을 실제 호출에 전달한다. 미지원 값 자동 강등·다른 provider 자동 전환은 금지한다.
- 작업당 최대 LLM 턴·도구 호출 수·총 시간·출력량·사용량 한도를 둔다. 무한 수정/실행 루프를 금지한다.
- provider 문맥은 user + room + project 경계로 구성한다. 다른 사용자 대화·작업 로그·공용 CLI 세션을 재사용하지 않는다.
- credential을 격리 코드에 제공하지 않는다. 중앙 LLM 호출과 생성 프로그램 실행을 분리한다.

## 10. 공용 프로그램 제어 계약

- superadmin이 서버의 프로그램을 등록한다. ProgramDefinition은 수정 가능한 일반 프로젝트 밖에 둔다.
- 일반 요청에는 `program_id`, 허용된 `action`, 제한된 `params`만 허용한다. executable, cwd, 임의 shell 문자열, 실행 계정을 받지 않는다.
- 고정 실행 파일의 경로·파일 정체성·정책 revision을 확인한다. 사용자 쓰기 가능한 실행 파일을 특권 프로그램으로 등록하지 않는다.
- 실행 인자는 배열로 구성하고 옵션·경로·길이·값 범위를 검증한다. 문자열 치환으로 `cmd /c`나 PowerShell 명령을 만들지 않는다.
- 필요 권한은 프로그램·동작별로 최소화한다. 생성 코드나 사용자가 바꿀 수 있는 스크립트를 상승 권한으로 실행하는 기능은 제공하지 않는다.
- 공용 프로그램 시작·종료와 설정 변경은 동작별 grant 및 필요 시 승인 정책을 적용한다. 이미 허용된 일반 동작을 매번 다시 승인받지는 않는다.
- 프로그램 인스턴스 소유자, PID뿐 아니라 생성 시각·실행 경로·작업 ID를 추적한다. PID 재사용으로 다른 프로세스를 제어하지 않는다.
- 이미지 이름만으로 프로세스를 일괄 종료하지 않는다. 정상 종료를 우선하며 강제 종료 권한은 별도로 둔다.
- 공용 자원은 program/resource 잠금으로 충돌을 막는다. 서로 독립된 개인 작업은 제한 안에서 병렬 실행한다.
- 시스템의 기존 업무 프로그램을 테스트 대상으로 사용하지 않는다. 무해한 전용 fixture로 실행·상태·종료를 검증한다.
- 화면 조작이 필요한 프로그램은 별도 로그인 세션 helper가 필요하다. 세션 0 서비스에서 직접 마우스·키보드 조작을 해결하려 하지 않는다.
- 향후 GUI 자동화는 공용 desktop 단위의 단일 실행 잠금, 허용 창·프로그램 범위, 로그아웃/잠금 시 unavailable 상태를 요구한다. 같은 화면의 동시 사용자 조작과 사용자별 화면 비밀 보장을 주장하지 않는다.

## 11. 작업 상태, 중복, 취소, 재시작

권장 상태: `queued → planning → running → completed / failed / cancelled / interrupted`.
정책상 승인이 필요한 도구 단계에만 `awaiting_approval`을 사용한다. 실제 상태명은 통일해서 서버·UI·테스트에 적용한다.

- AgentJob은 AIRequest와 구분하되 room/source message로 연결한다. 기존 대화 생성 큐를 두 번 호출하지 않는다.
- `(owner, project, client_id)` 중복을 저장 트랜잭션에서 검사한다. 같은 ID·다른 내용은 409로 거절한다.
- 도구 단계는 별도 tool_call_id로 중복 방지한다. 외부 프로그램 부작용에 대해 근거 없는 exactly-once 보장을 하지 않는다.
- host 동작의 결과가 불명확한 상태에서 서버가 죽으면 재시작 후 자동 재실행하지 않는다. 상태 확인이나 명시적 재시도 대상으로 남긴다.
- 파일 patch는 예상 revision/hash를 받는 방식으로 덮어쓰기 경합을 처리한다.
- 취소는 실제 LLM 요청, 실행 Job, 자식 프로세스에 연결한다. terminal 상태를 늦게 온 결과가 completed로 바꾸지 못한다.
- 권한 회수와 활성 작업 취소를 연결하고 다음 tool 실행 직전에도 검사한다.
- 완료 후 산출물 등록은 검증된 파일만 한다. 사용자가 해당 프로젝트에 접근할 수 없으면 결과도 노출하지 않는다.
- 재시작 시 남은 활성 작업은 interrupted로 정리한다. 프로그램이 이미 바꾼 외부 상태와 결과 파일의 존재는 별도 확인한다.
- 프로젝트별 쓰기 작업은 직렬화하거나 명시적 충돌 제어를 적용한다. 동시에 같은 파일을 고치는 두 에이전트를 방치하지 않는다.
- 서버 Close/startWorkers/설정 재적용 수명주기에 작업자 종료·대기·프로필 정리를 통합한다.

## 12. API 계약과 UI

아래 API는 권장 명칭이다. 기존 관례로 조정하면 문서·서버·클라이언트·테스트를 함께 맞춘다.

| API | 동작·필수 검사 |
|---|---|
| `GET /api/ai/friends` | 공개 AIProfile·사용 가능 상태, 비밀 제외 |
| `POST /api/ai/friends/{id}/open` | 본인 기본 AI 방 멱등 생성/열기 |
| 기존 AI 새 방 API | 새 문맥 생성, profile 연결 |
| `GET/POST /api/agent/projects` | 접근 가능한 project 목록·본인 project 생성 |
| `GET/PATCH /api/agent/projects/{id}` | 소유권/위임, revision, 활성 상태 검사 |
| `POST /api/agent/jobs` | room/project 일치, 작업 모드, model/effort, 한도, client_id 검사 |
| `GET /api/agent/jobs/{id}` | 현재 권한 검사 후 상태·제한된 로그 |
| `POST /api/agent/jobs/{id}/cancel` | 본인/위임 작업 취소 |
| `POST /api/agent/jobs/{id}/retry` | 새 idempotency key, 부작용 불명확 단계 자동 반복 금지 |
| `GET /api/agent/artifacts/{id}` | 다운로드 시 소유권·최종 파일 경로 검사 |
| `GET /api/agent/programs` | 해당 사용자에게 허용된 프로그램·동작만 |
| `POST /api/agent/programs/{id}/actions` | 중앙 정책과 공용 자원 잠금을 거치는 작업 생성 |
| 관리 설정 확장 | 역할·grant·실행기·toolchain·program·quota 관리 |
| 실행기 진단 API | 설정 관리자만, 환경 확인과 실제 격리 self-test 결과 구분 |

- 요청 schema는 알 수 없는 특권 필드를 거절한다. 오류는 400/401/403 또는 존재 은닉용 404/409/429/503을 일관되게 사용한다.
- 일반 사용자에게 실제 호스트 경로·다른 프로젝트 ID 목록·실행 계정·credential을 반환하지 않는다.
- SSE는 사용자별로 필터링한다. 기존 sync 재사용 또는 전용 이벤트 중 하나를 선택하고 재연결·계정 전환 시 이전 사용자 데이터가 남지 않게 한다.
- 파일 내용·로그·AI 응답은 비신뢰 텍스트로 렌더링한다. HTML을 그대로 삽입하지 않는다.
- 산출물은 적절한 MIME, attachment 다운로드, nosniff를 사용한다. 생성 HTML/JS를 인증된 앱과 같은 origin에서 실행시키지 않는다.
- UI에는 현재 mode, project, model/effort, 단계, 중지, 결과 파일, 실패 이유, 사용 한도를 표시한다.
- 기존 Android WebView 공통 UI를 재사용한다. 별도 네이티브 UI를 중복 구현하지 않는다.
- 모델이 비활성화된 기존 방에서도 가능한 모델로 변경할 수 있어야 한다. 현재 모델이 없다는 이유로 모델 선택까지 모두 잠그지 않는다.

## 13. 설정·설치·버전·보관

- 실행기 활성화, workspace root, toolchains, 사용자 quota, 기본 네트워크 정책, 프로그램 정의를 기존 설정 저장/적용 구조에 통합한다.
- 예시 경로는 `D:\OnTechChatData\workspaces`이지만 D: 존재를 설치 요구로 고정하지 않는다. 기본값은 기존 데이터 루트 아래의 관리된 하위 폴더로 정하고 관리자가 변경 가능하게 한다.
- workspace root 변경은 단순 문자열 갱신으로 처리하지 않는다. 활성 작업 차단, 기존 파일 이행/유지 정책, 권한 재설정, 실패 복구가 필요하다.
- 새 비밀값이 있으면 기존 암호화 저장 계층을 사용하고 GET 응답에서 제외한다.
- 설치기는 필요한 실행 모드·파일·ACL·실행 환경 진단을 포함하되 기존 데이터·서비스·트레이·제거 정책을 보존한다.
- 제거 시 사용자 workspace를 무조건 삭제하지 않는다. 기존 제품의 명시적인 데이터 삭제 선택을 따른다.
- 버전은 착수 시 실제 최신값을 기준으로 증가시킨다. 1.12.0이 여전히 최신이면 다음 서버 기능 버전은 1.13.0을 권장한다. 기존 1.12.0 배포 파일을 같은 버전으로 덮어쓰지 않는다.
- 서버·설치기·트레이·웹 표시·manifest를 일치시킨다. Android 네이티브 변경이 없으면 불필요한 APK 버전 증가를 강제하지 않는다.
- 설정·스토어 schema 이행에 대해 롤백 가능한 백업과 지원 범위를 명시한다. 신버전 데이터를 구버전이 안전하게 읽는다고 가정하지 않는다.

## 14. 단계별 수행과 통과 조건

### 단계 A — 현재 상태·변경 계획

- 최신 지침·상태·코드를 읽고 중복 작업·버전·기존 변경을 확인한다.
- `.build\ai-friend-agent-change-plan.md`에 수정 파일, 데이터 이행, 역할 정책, Windows 실행 환경, 테스트 명령을 기록한다.
- 변경 전 백업은 `.build` 아래에 제한해서 만들고 credential·운영 데이터의 불필요한 복사를 피한다.

통과: 구현할 범위와 현재 미구현 기능을 분리해 기록했고 실행 중 다른 작업과 충돌하지 않는다.

### 단계 B — AI 친구와 역할·프로젝트

- AIProfile, 기본 방 연결, UI, 기존 AI 방 이행을 구현한다.
- 중앙 권한 함수, 역할 이행, grant, project API·저장을 구현한다.
- AI 친구에서 질문·답변이 기존 실제 provider 경로로 이어지는지 확인한다.

통과: 두 사용자의 친구·방·문맥이 독립이며 API 직접 호출로 상위 권한이나 타 사용자 자원을 얻을 수 없다.

### 단계 C — 실행기 실증과 운영 인터페이스

- AppContainer 생성·토큰 확인·전용 경로 ACL·Job Object·IPC를 구현한다.
- Go 기반 무해한 프로그램을 실제 제한 프로세스에서 빌드하고 실행한다.
- 타인/서버 비밀 파일, 네트워크, 외부 프로세스 접근을 시도하는 테스트 fixture가 실제로 차단되는지 검증한다.
- 취소 시 부모·자식 종료와 서버 종료 복구를 확인한다.

통과: 실행 성공 증거와 차단 성공 증거가 모두 있다. mock만 통과한 실행기를 ready로 표시하지 않는다.

### 단계 D — LLM 도구 루프와 결과 전달

- 지원 provider 한 개 이상에서 실제 구조화 도구 요청 왕복을 구현한다.
- 사용자 작업 요청으로 코드 생성 → 검증된 write → 빌드 → 실행 → artifact → 채팅 결과까지 연결한다.
- 무한 루프, 중복 도구 호출, 취소, 권한 회수를 처리한다.

통과: 하드코딩된 파일 생성 예제 대신 모델이 생성한 무해한 프로그램으로 end-to-end 동작한다. mock wire 테스트와 실제 provider 검증을 구분한다.

### 단계 E — 등록 프로그램 제어

- 고정 프로그램 등록·동작 schema·grant·resource lock을 구현한다.
- 테스트용 프로그램의 시작·상태·정상 종료를 실제 수행한다.
- 미등록 경로·임의 명령·사용자 수정 실행 파일·타인 프로세스 제어가 차단된다.

통과: 채팅 작업이 실제 등록 프로그램의 허용 동작을 수행하며 사용자·정책·결과가 감사 기록에 남는다.

### 단계 F — 통합 검증·공식 빌드·문서

- 아래 검사표와 관련 기존 회귀를 실행한다.
- `build.ps1`의 테스트 선택에 새 권한·실행기·Agent 검사를 포함한다. 기존 Core 필터가 `Test(Location|AllFriends|AI)`였다는 점을 고려해 새 이름의 테스트가 빠지지 않게 한다.
- 공식 서버 설치기를 만들고 버전·payload·SHA256을 확인한다.
- 기능별 완료/부분 완료/환경 차단을 기록한다. 설치기 준비를 운영 설치 완료로 보고하지 않는다.

| 네트워크·IPC | 외부·loopback·내부 관리 API 우회 차단, 다른 job 권한 재사용 거절 |
| LLM tool loop | 올바른 도구 왕복, 잘못된 schema·도구명·권한 필드 거절, step limit |
| prompt injection | 프로젝트/로그의 특권 지시로 허용 도구·경로·역할이 확대되지 않음 |
| 중복·복구 | client_id·tool_call_id 중복 처리, 재시작 후 불명확한 host 동작 자동 반복 없음 |
| 공용 프로그램 | grant·동작 제한, 고정 인자, resource lock, PID 재사용·경로 교체 방어 |
| 표시·다운로드 | XSS성 로그·HTML 산출물 안전 처리, 계정 전환·SSE 정보 누출 방지 |
| 기존 회귀 | 사람 친구, 그룹 채팅, 인증함, 위치 조회, 알림, 설정 적용, 설치 수명주기 |

테스트 수준을 구분해서 기록한다:

- 단위/mock: 권한 결정, wire schema, 상태 전이, 데이터 이행.
- 실제 Windows 통합: 보안 토큰·ACL·프로세스·IPC·네트워크·취소.
- 실제 LLM: 설치된 사용 가능 provider로 무해한 최소 작업 1회. 사용량이 발생한 검증임을 기록한다. credential이 없으면 mock과 실제 Windows 검증을 계속 수행하고 실제 LLM 항목은 미검증으로 남긴다.
- 실사용: 로그인한 서버 세션·운영 서비스 계정·Android 실제 기기 검증은 수행 여부를 각각 표시한다.

격리 검증을 통과하지 못했으면 agent를 enabled/ready로 출시하지 않는다. 반대로 모든 검사가 충분히 통과한 뒤 관련 없는 전체 검사를 반복해서 작업을 지연하지 않는다.

## 16. 코드 구성 제안

다음은 새 파일 후보이며 실제 프로젝트 구조에 맞춰 조정한다. 한 거대 파일에 전 기능을 넣지 않는다.

- `server/ai_friends.go`: AIProfile, 기본 방 연결, 공개 친구 API.
- `server/authorization.go`: 역할·grant·대상 권한 검사.
- `server/agent_config.go`: agent 설정·지원 capability·진단 상태.
- `server/agent_projects.go`: 프로젝트 저장·소유권·quota.
- `server/agent_jobs.go`: 작업 큐·상태·중복·취소.
- `server/agent_coordinator.go`: LLM 도구 왕복·단계 한도.
- `server/agent_tools.go`: 도구 schema·검증·dispatch.
- `server/agent_artifacts.go`: 산출물 등록·조회·다운로드.
- Windows 실행 모듈: AppContainer, 토큰, ACL, Job Object, IPC, toolchain 진단.
- `server/host_programs.go`: 등록 프로그램·허용 동작·자원 잠금.
- UI: 기존 messenger/settings와 필요 시 분리한 agent 화면 모듈.
- `*_test.go`: 권한·저장 테스트와 실제 Windows 전용 검사를 분리.

Go 실행기의 Windows API 의존성은 기존 모듈과 설치기 구조를 확인해 최소한으로 추가한다. 새 패키지 선택 이유와 실제 버전을 기록한다. 불필요한 외부 서비스·DB·Docker 의존성을 추가하지 않는다.

## 17. 진행 기록과 최종 보고

작업 중에는 `docs\AI_FRIEND_AGENT_PROGRESS.md`에 현재 단계, 수정 파일, 완료 검사, 정확한 다음 작업, 차단 항목을 갱신한다. 중단돼도 다음 모델이 이어갈 수 있어야 한다.

최종 답변에는 다음을 명확히 적는다.

- 이전/새 버전과 변경된 사용자 동작.
- AI 친구에서 질문·작업을 시작하는 방법.
- 실제 지원한 provider·toolchain·등록 프로그램 동작.
- 실제 Windows 격리 검증 결과와 테스트가 강제한 범위.

- 남은 차단 항목과 재현 가능한 원인. 미구현·mock·미검증을 구현 완료에 포함하지 않는다.

## 19. 개발 모델이 마지막으로 자가 확인할 항목

- [ ] 사용자별 OS/VM 없이 같은 서버 Windows에서 처리하는가?
- [ ] AI 친구를 눌러 실제 개인 대화가 열리는가?
- [ ] user/admin/superadmin 구분과 대상별 권한이 서버·실행기 양쪽에 적용되는가?
- [ ] 폴더 분리뿐 아니라 실제 Windows 토큰·ACL·프로세스 격리를 검증했는가?
- [ ] LLM의 구조화 도구 요청이 실제 파일 작성·빌드·실행·결과 저장으로 이어지는가?
- [ ] 서버 credential과 관리자 권한을 생성 코드에 전달하지 않는가?
- [ ] 등록 프로그램 제어가 임의 호스트 명령 실행 통로가 되지 않는가?
- [ ] 취소·권한 회수·재시작·중복 요청을 실제 작업 상태와 연결했는가?
- [ ] 기존 위치·인증함·채팅·설치 기능을 보존했는가?
- [ ] 구현, mock, 실제 검증, 공식 빌드, 운영 적용을 구분해 보고했는가?

이제 위 순서에 따라 구현을 시작하라. 환경상 차단된 단계가 있으면 그 기능은 닫고 나머지 독립적인 구현·검증·문서를 완료하라. 보안 경계를 없애거나 가짜 성공으로 대체하지 말라.
